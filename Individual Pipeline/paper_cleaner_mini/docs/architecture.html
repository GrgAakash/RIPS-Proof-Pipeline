Paper Cleaner Mini · Design Document

Three roles, one gate:
the architecture of a minimal problem-setting pipeline

paper_cleaner_mini is the minimal counterpart to the main repo's 8-step graph pipeline: three gpt-5.5 roles that each hold the full paper (author / adversarial checker / repairer) plus one deterministic gate, turning target theorems of arXiv math papers into self-contained, leak-proof "prove this theorem" problem packages. No dependency-graph parsing, no text-matching ladder — the main repo's 46 engineering lessons are all distilled into the prompts, not the code.

The Mini runtime is standalone: it imports only this folder's support files. Third-party paper inputs are deliberately git-ignored and must be prepared locally.

§1 · ARCHITECTURE

Overall architecture: a five-stop data flow

The whole system is a one-way data flow: material in, problem packages out, a referee to accept them. Each of the five nodes reads only the previous stop's artifacts; there is no hidden state between them.

inputs/ Paper material flat.tex full text · meta · statement index · target selection (from main-pipeline steps 1–5)
→
stage2.py Generation loop author → gates → checker → repair; targets run concurrently, independently
→
runs/ Packages + ledger problem.md · frozen target.tex/target.json · manifest · excluded.json · cache · logs
→
audit.py Independent audit an audit-grade model re-checks every package and every exclusion against the paper
→
compare_audits.py Comparison verdict side by side vs the main-pipeline baseline: clean rate · fatals · false kills
Shared substrate: minilib.py — config / RunContext / LLM layer (cache · rate-limit retries · structured output) / schemas / deterministic checks prompts/ — where all behavioral rules live config.yaml — concurrency · token budgets · cache switch

Fig. 1 · Data flow and shared substrate. The output layout is byte-compatible with the main pipeline's, so both sides can be accepted by the same audit program.

Design principles: three things inherited from the main pipeline

  • Generator ≠ verifier — authoring and checking are always two independent calls; the checker's stance is set by its prompt to "refute the author's three claims";
  • Deterministic backstop — where the LLM's word doesn't count (verbatim overlap, macro closure, section structure), pure code decides, and passing is mandatory before shipping;
  • Honest exclusion — problems that can't be repaired don't ship; every exclusion carries a reason code and its unresolved items, open to audit review.

§2 · CONTROL FLOW

Per-target control flow

Each paper's attack targets = the main pipeline's selection (mains ∪ hardest; 19 across the four papers). Targets are independent of one another and run concurrently (semaphore default 8). The lifecycle of a single target:

Fig. 2 · Per-target control flow. ①③④ are LLM calls (red outline), ② is pure code; each round = one gate pass + one check.

Exact ship / exclude rules

  • Ship condition (all required): all three checker verdicts true, no fatal issue, zero deterministic-gate hits;
  • Exclusion reason codes (mapped by priority): uncleared leak → leak_in_required_context; symbol/term gaps → self_containment_unresolvable; missing tools → sufficiency_unresolvable;
  • Round ledger: a snapshot before each repair round is saved as problem.iterN.md; on exclusion the final draft and report are kept for the post-mortem.

§3 · ROLES

The three LLM roles: who sees what

By default the three roles share one model (auto-selected strongest tier available to the account — gpt-5.5 in the experiment, reasoning effort = high; --check-model can point the checker at a different model). The differences live entirely in each prompt's field of view and stance. The target theorem's own proof is fenced off as the forbidden zone (forbidden_source): the author and repairer may read it to judge which prerequisites the solver will need, but not one sentence of it may enter the problem.

① author · problem setter

prompts/s2_author.txt · once per target (+1 retry on bad format)
Sees
full paper · target statement · forbidden proof · the paper's macro table
Produces
editable Sections 0–5 only; the header and immutable source-backed Section 6 are stitched on by code
Key rules
verbatim quotes first, never invent mathematics; external results transcribed in full (usage-quotes banned); references must resolve within the file

③ checker · adversarial review

prompts/s2_check.txt · once per round
Sees
full paper · current problem file · target proof (as the sufficiency reference)
Produces
issue list (fatal/minor + actionable fix_hint) + three verdicts: self-contained / leak-free / sufficient
Key rules
stance = refute; a granted statement's presence is not a leak — narrating the proof idea is; instances of parameterized notation count as defined; local steps re-derivable in ~3 lines are not gaps

④ repair · repairer

prompts/s2_repair.txt · at most 2 rounds
Sees
full paper · current file · findings (checker fatals + gate hits) · forbidden proof
Produces
complete revised Sections 0–5 + an unfixed list; it never writes the target section
Key rules
fill gaps with the paper's own text; results may only be quoted, never synthesized; when rewriting a leak, keep the legitimate bare grant; forbidden material never enters

§4 · DETERMINISTIC GATE

The deterministic gates: four things the LLM doesn't get to decide

Before each checker round, pure code runs three checks; any hit enters repair as a fatal finding and single-handedly vetoes shipping. This layer shares its algorithms with the main pipeline's audit scans, so both sides are measured with the same ruler.

  1. Section-structure check — the model's six editable headings must all be present and in order (## 0. Macro definitions … ## 5. Available results). Bad format → one re-ask; the controller then appends Section 6 itself.
  2. Macro closure — every non-standard LaTeX command appearing in the file must be defined in the file's own Section 0. Stricter than the main pipeline's g3: g3 accepts "defined in the paper's preamble"; mini requires the problem to render on its own.
  3. Verbatim-proof leak scan — the target proof's normalized text slides over the whole file in 120-character windows (Section 3's external-results area gets an extra 50-character floor); any hit is fatal. Whitelist = target statement + macros + verbatim-quoted index blocks; usage-quotes are never exempt.
  4. Target-integrity gate — only deterministic parser entries with a valid source span and matching statement/source hashes may be targets; target.tex, target.json, Section 6, the independent audit, and the solver export must all agree exactly. Theorem numbers are never synthesized or used as IDs; uncertainty causes exclusion, never reconstruction.
Field record: across the four-paper batch, the gates caught verbatim proof overlap at least 4 times on files where the checker had all three verdicts green — the "LLM check + deterministic backstop" layering is not a fuse, it is a routine worker.
Cautionary tale (since fixed): the standard-command whitelist initially missed providecommand, so the repairer's perfectly legal fix line \providecommand{\mathds}… was itself judged an illegal command — unrecoverable by construction — and two lemmas were wrongly killed. Lesson: wherever the LLM has free rein, the deterministic whitelist must cover every legal form it might use.

§5 · ARTIFACTS & CACHE

Artifacts, cache, and resumable runs

paper_cleaner_mini/ ├── stage2.py generation loop (all of §2's control flow) ├── audit.py independent audit referee ├── compare_audits.py side-by-side comparison of two audit reports ├── minilib.py config / LLM layer / schemas / deterministic checks ├── config.yaml · requirements.txt · README.md ├── prompts/ s2_author · s2_check · s2_repair · audit_pkg · audit_excl ├── data/latex_std_commands.txt ├── inputs/<paper>/ flat.tex · meta.json · statements.v2.json · selection.json └── runs/<paper>/ output (layout-compatible with the main pipeline) ├── manifest.json ★ problem manifest (for downstream) ├── packages/<target>/stage2/ │ ├── problem.md ★ the problem itself │ ├── target.tex · target.json ★ exact target text + source/hash provenance │ ├── problem.iterN.md per-round snapshots (for the post-mortem) │ ├── report.json · assembly.json ├── excluded.json honest ledger: reason code + details for every exclusion ├── cache/ LLM call cache (the key to resumable runs) └── logs/run.jsonl structured log: one line per call

Cache key = model + prompt-template hash + all variable bindings + schema name + sampling params. Identical input always hits; any change anywhere always misses — so re-running as-is is always free, and editing a prompt recomputes only the affected calls.

Example: after the whitelist fix, re-running 2606.19639 hit the cache on all 24 calls — zero live calls, done in about a second — and the two wrongly-killed lemmas shipped straight away under the gates' new verdict, at zero cost.

§6 · EVIDENCE

Relation to the main pipeline, and what earns the "mini"

mini deliberately reuses the main pipeline's target selection (the same 19 targets) and the same audit referee, collapsing the experimental variable to one question: on the "package + verify" segment, which does better — the graph machinery, or a strong model reading the paper directly. The statement index supplies the target statement/proof, immutable source span and hashes, macro table, and whitelist text for the leak scan — the dependency graph is never read.

Reservation (twin referees): mini's in-loop checker and the audit referee are the same model on nearly the same task, so the 16/16 may be inflated. The relative conclusion (mini ≥ pipeline) is solid; the absolute "zero defects" should be re-confirmed with a different referee (e.g. --model o3 for the audit, or stage2's --check-model) or by manual spot checks before it is final.

Experiment totals: 99 live calls, 4.1M input / 0.67M output tokens (0.51M of it reasoning); about 35 minutes end to end with three papers in parallel × concurrency 8.

§7 · QUICKSTART

The whole flow in three commands

# setup (once): python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
export OPENAI_API_KEY=sk-...

.venv/bin/python stage2.py --papers all --parallel 8     # generate (--dry-run previews the plan for free)
.venv/bin/python audit.py  --papers all --effort high    # independent audit → runs/audit/audit_report.md
.venv/bin/python compare_audits.py \
    ../paper_cleaner/runs/audit/audit_report.json \
    runs/audit/audit_report.json                          # side by side vs the main pipeline → comparison.md

Adding a paper: run the main repo through step 5, then copy the four files flat.tex / meta.json / statements.v2.json / selection.json into inputs/<arxiv-id>/. mini is the comparison arm of an experiment — download and parsing are deliberately left out (for now).
